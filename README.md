# Evolution24 Properties — evolution24.net

The redesign of evolution24.net, the family-owned property manager with apartments in
Rochester, Syracuse, Manlius and Geneva, New York. It replaces the Rent Manager
WordPress theme with a fast static site, built the same way as its sister site
[charlottesquareroc.com](https://github.com/1800bobrossdotcom-byte/50CharlotteSquare).

Nothing on the old site was kept except the photographs and the facts. Every photo
and every fact on the old site is here.

No framework and no runtime dependencies: plain HTML, one stylesheet and one script.
The HTML is generated by a Python script from two JSON files.

## Build

```bash
python3 scripts/photos.py        # when photos change (needs Pillow with AVIF support)
python3 scripts/build.py         # always — writes every page into the repo root
node scripts/render-og.cjs       # when a name, a cover photo or a unit count changes, then build again
node scripts/render-icons.cjs    # when the logo changes (needs Playwright)
python3 -m http.server 8000      # preview at http://localhost:8000
```

| Edit this | To change |
| --- | --- |
| `data/properties.json` | A building's name, address, map coordinates, description, amenities, **available units and rents**; each city's blurb and share-card photo |
| `source/photos/manifest.json` + `source/photos/<slug>/` | Photos and their alt text, then run `photos.py` |
| Constants at the top of `scripts/build.py` | Phone, email, office address, portal links, pet policy, FAQs |
| `assets/css/main.css` | The design. Everything below the `GENERATED` line is rewritten by the build |
| `assets/js/main.js` | Behaviour |

Never hand-edit the generated `*.html`, `sitemap.xml`, `llms.txt`, `speculation-rules.json`, `vercel.json`,
`_headers`, `_redirects`, `assets/img/og/` or `data/page-dates.json`. Do commit them all.

## Pages

| URL | What it is |
| --- | --- |
| `/` | Intro animation, hero slideshow, the three regions, photo band, every available unit, about, residents, contact |
| `/properties/` | All 11 buildings, filterable by region and by availability, plus the full unit list |

| `/about-us/`, `/faqs/`, `/contact-us/` | Same URLs as the old site, so no rankings are lost |
| `/privacy/` | Fair housing, privacy and accessibility statement |
| `404.html` | Not found |

`/about-us/`, `/faqs/`, `/contact-us/` and `/properties/` keep their old addresses on purpose.
The old URLs that are going away are redirected:

| Old | New | How |
| --- | --- | --- |
| `/property-detail/?pid=8` | `/properties/water-street/` | 301 from `vercel.json`, matched on the query string; `assets/js/legacy.js` elsewhere |
| `/unit-detail/?uid=62` | `/properties/water-street/#units` | same, one per available unit |
| `/careers/` | `/about-us/` | 301 from `vercel.json` (or `_redirects`), plus a stub page |
| `www.evolution24.net/*` | `evolution24.net/*` | 301 from `vercel.json` (or `_redirects`) |

On Vercel the query-string redirects are real 301s, so the rankings of the old building
pages pass to the new ones. Other static hosts can't match a query string, so the stub
pages stay as a fallback: they are `noindex` and redirect in the browser. `robots.txt` no
longer blocks them, because a crawler that can't fetch an old URL never sees its redirect.

## Logo and animation

The logo is traced from the owner's PSD (`source/logo/Evolution24_Properties_logo.psd`,
four layers at 6000 × 2460). Each bar of the mark and each letter of the wordmark is its
own path. That is what makes it animate:

- **Intro.** Only when a visit starts on the home page, the bars rise one by one from the
  baseline, the letters settle in, and the curtain lifts. The whole thing takes 2.9 s, and
  1.75 s on a phone. A click or any key skips it. It is skipped entirely under
  `prefers-reduced-motion`, and a `sessionStorage` flag makes sure it never plays twice in a
  visit, or at all when the visit starts on another page (someone arriving from a search
  result for a building wants the building). The page underneath has already loaded, so the
  intro never delays content.
- **Header.** The bars rebuild on every page load and ripple on hover.
- **Everything else.** Masked headline rises, a Ken Burns hero slideshow, scroll reveals and
  image wipes, count-up stats, an index of every building under the hero (names rise in turn;
  hovering one inks it tan and shows its city and how many homes are open), photo rows that drift with the
  scroll (CSS scroll timelines, where supported), filter transitions and cross-page
  transitions (View Transitions API, where supported).

**Reduced motion is reduced, not removed.** When a visitor's device asks for less motion
(Windows "Animation effects" off, macOS/iOS "Reduce motion", Android "Remove animations"),
nothing slides, zooms, scrolls or auto-advances, but pages still fade in and hovers still
change colour. The intro is skipped and the slideshow waits for a click. Test both: Chrome
DevTools → Rendering → "Emulate CSS media feature prefers-reduced-motion".

**After Effects.** `tools/after-effects/` turns the same logo and animation into an After
Effects project. `python3 tools/after-effects/make.py` writes `evolution24-logo.jsx`. Run that
in After Effects (File > Scripts > Run Script File) and it builds three comps:
- the intro at 16x9, as on a laptop;
- the intro at 9x16, in its phone timing;
- the header lockup's build, on transparency.

Every bar and letter becomes a native shape layer, keyframed with the site's own timing. The
easing curves are converted exactly into speed and influence. The script then saves the `.aep`
beside itself. `make.py` reads the paths from `source/logo/logo_vec.json`. It stops if
`main.css` no longer says what its timing table assumes. It also builds the kit to hand over in
`tools/after-effects/out/`: the script, the SVGs, a README and the reference videos, zipped.
- `node tools/after-effects/reference.cjs` records the site's own animations at 60 fps, as the
  kit's reference videos. Run it before `make.py`.
- `node scripts/test-after-effects.cjs` runs the script against a mock of After Effects. The
  mock checks the script is ECMAScript 3, which is what ExtendScript runs. It also checks match
  names, stale references, and one ease per dimension.
- `node scripts/compare-after-effects.cjs` replays the keyframes the way After Effects
  interpolates them, and compares every frame with the site's animation in Chromium. It also
  checks that it would catch deliberate mistakes: everything 30 ms late, the logo 1% too big,
  or linear easing.

Logo files: `assets/img/logo.svg` (for dark backgrounds, as supplied), `logo-on-light.svg`
(the cream swapped for ink, so it reads on white), `mark.svg`, `favicon.svg`,
`favicon.ico`, `apple-touch-icon.png`, `logo-192.png`, `logo-512.png` and `og.png`, the
social share card.

## Site load

| | Size (gzipped) |
| --- | --- |
| Home page HTML, with the whole stylesheet inlined | 26 KB (the CSS is 9 KB of it) |
| `main.js` (deferred) | 4 KB |
| Preloaded fonts | 44 KB, plus 21 KB for the italic on the home page |
| Hero photo (AVIF) | 32–66 KB on a phone (49 KB on an iPhone, down from 95 KB), 85–125 KB on a desktop |

The old site shipped jQuery, Slick, Font Awesome, Google Fonts and a full WordPress theme.
Here:

- **Photos** are AVIF, with WebP for older browsers, at 240, 480, 720, 960, 1200, 1400,
  1600 and 2000 px. Each `<picture>` has `sizes` worked out from the layout, so a phone
  never downloads a desktop image. 1200 and 1400 exist for phones: a full-width photo on a
  3× screen needs 1170–1320 pixels, and used to get the 1600. The home page's hero on an
  iPhone is 49 KB, down from 95 KB. AVIF is about a quarter smaller than WebP at the same
  look. Every `<img>` has `width` and `height`, so
  nothing jumps as it loads. Only the hero photo loads eagerly, with `fetchpriority="high"`
  and an AVIF preload. Everything else is lazy. EXIF data is stripped, which removes the
  GPS location phones embed.
- **Fonts** (Manrope, Instrument Serif) are self-hosted, subset and preloaded. Until they
  arrive, text is set in local fallback fonts resized to the same measurements
  (`size-adjust` and the ascent, descent and line-gap overrides). That matches their
  average width, not every line break, so Manrope is `font-display: optional`: being
  preloaded, it is almost always ready for the first paint, and when it isn't, that one
  page stays in the fallback instead of swapping. A swap once re-wrapped the home hero's
  paragraph and buttons and moved the whole hero (Lighthouse: layout shift 0.19); now it is
  0. The display serif keeps `swap`, because its headings are set line by line and can't
  re-wrap.
- **CSS is inlined** into every page, minified, so the first paint waits on no request.
  The CSP allows it by its hash. Painting that early means a slow connection can show half
  a hero, and the home and building heroes are bottom-aligned, so the rest arriving would
  push their words up the screen. Their words therefore stay invisible, though in place,
  until the section after the hero has started to arrive (`:has(+ *)` in `main.css`).
- **Next pages are ready before the tap.** Speculation Rules (`speculation-rules.json`,
  sent in a `Speculation-Rules` header) let Chrome and Edge prerender a page while a
  visitor hovers over its link or starts to press it, so most navigations are instant. `/api/`, the redirect
  stubs and files are excluded. Other browsers ignore it.
- **Phones.** Every link and button is at least 44 px tall on a touch screen (padding taken
  back with negative margin, so the design doesn't move). Long button labels wrap instead
  of pushing the page sideways, and nothing scrolls sideways at 360 px. On a building's
  page, a bar with **Call** and the building's next step (see what's available, join the
  waitlist, or visit Charlotte Square's site) slides up once the hero's buttons have
  scrolled away, and gets out of the way over the footer.
- **Maps** load nothing from Google until someone presses "Show the map".
- **Caching:** CSS and JS are requested as `?v=<content hash>` and cached for a year as
  immutable. Images are cached for 30 days.
- **No third-party requests at all, and no cookies for visitors.** The site counts its own
  visits on its own server (see *Statistics and the dashboard*), keeping no IP address, so
  there is nothing for a consent banner to ask about.

## SEO

- **One host.** `SITE = https://evolution24.net`, the apex that the old site already used
  as its canonical. `www` 301s to it.
- **Titles and descriptions** are written per page, include the city and the category
  ("apartments"), and stay under Google's truncation length. Descriptions are built from
  whole sentences (`fit()` in `build.py`), so none is ever cut mid-word, and lead with the
  facts people search for: bedrooms, address, how many are available, and the rent.
- **City pages** (`/apartments/<city>-ny/`) answer "apartments in Rochester, NY" and its
  like: every building and every open unit in that city, with `CollectionPage`, `ItemList`
  and `FAQPage` markup. Building pages link up to their city, in the breadcrumb and the
  text, and the footer links all three.
- **Structured data.** Every page carries one JSON-LD `@graph`: `WebSite`, a
  `RealEstateAgent` for Evolution24 (`#organization`, with address, phone, founding date,
  the four cities it serves, and `sameAs` pointing to Charlotte Square), `WebPage` and
  `BreadcrumbList`. The organization also has its logo, the office's coordinates and a
  leasing `ContactPoint`. Each building page adds an `ApartmentComplex` or `Residence` with
  its address, coordinates, photos, amenities, map link, price range, its city, and one
  `Apartment` for each available unit. `/faqs/` adds `FAQPage`, `/properties/` adds an
  `ItemList`. Every page names its share card as `primaryImageOfPage` and carries a
  `dateModified`. Validate at <https://validator.schema.org/>.
- **Coordinates** for each building were looked up from its street address in
  OpenStreetMap and are stored as `geo` in `data/properties.json`.
- **Sitemap** with Google image entries for 107 photographs. Each URL's `lastmod` is the
  day that page's content last changed, not the day of the last build:
  `data/page-dates.json` keeps a fingerprint of every page, and the date moves only when
  the fingerprint does. Search engines ignore a `lastmod` that changes on every build.
- **Share cards.** Every building and city, and the site itself, has its own 1200 × 630
  link preview (`assets/img/og/`, drawn by `scripts/render-og.cjs`): the photo, the logo,
  the name, and how many homes are open. So a link texted to a friend shows the building.
- **Alt text.** Every photo has a written description, in `source/photos/manifest.json`.
- **`robots.txt`** allows everything, including the AI crawlers. **`llms.txt`** is a
  plain-language fact sheet that lists every building and every available unit.
- **Charlotte Square.** Its page here points to charlottesquareroc.com. The Charlotte site's
  JSON-LD already names Evolution24 as its manager. Linking its `#management` node to
  `https://evolution24.net/#organization` would join the two sites into one entity.

After launch:

1. Verify `evolution24.net` in Google Search Console and Bing Webmaster Tools, then submit
   `sitemap.xml`.
2. Claim or update the **Google Business Profile** for the office at 176 N Water Street,
   with this URL. For "apartments in Rochester" it is worth more than anything on the page.
3. Check that `curl -sI https://www.evolution24.net/` returns a single 301 to the apex.

## Deploy

**Live on Vercel:** <https://evolution24-net.vercel.app/>. Vercel deploys every push, with no
build step: the generated site is committed, and Vercel publishes the repo root. Build logs
and the list of deployments are in the Vercel dashboard, under the **evolution24-net**
project. The branch Vercel treats as production is the repository's default branch.

Headers and redirects are generated in two dialects from the same lists in `build.py`:
`vercel.json` for Vercel, and `_headers` + `_redirects` for Cloudflare Pages or Netlify,
which Vercel ignores. `.vercelignore` keeps the sources out of the deployment: the logo
PSD, the original photos (13 of them carry GPS data), `scripts/` and `data/` are not
served.

The `vercel.app` address sends `X-Robots-Tag: noindex`, so search engines index only
`evolution24.net` and not a duplicate of it. `vercel.json` also sets `trailingSlash`, so
`/about-us` redirects to `/about-us/`, the canonical form.

| Header | Value |
| --- | --- |
| `Content-Security-Policy` | `default-src 'self'`, no `'unsafe-inline'` on scripts or styles. The one inline script, the intro flag in `<head>`, and the inlined stylesheet are allowed by their SHA-256 hashes, which the build computes from the same strings it emits. Frames are limited to Google Maps |
| `Speculation-Rules` | Points Chrome at `speculation-rules.json` (see *Site load*) |
| `Strict-Transport-Security`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Cross-Origin-Opener-Policy`, `Permissions-Policy` | Locked down |

Because the CSP forbids `style=""` attributes, animation stagger is done with generated
`.d0…d39` and `.i0…i11` classes rather than inline custom properties.

GitHub Pages can't set headers. There, only the `<meta>` CSP applies.

**DNS cutover.** The current site is WordPress. In Vercel, add `evolution24.net` as the
project's primary domain and `www.evolution24.net` as a redirect to it, then point DNS at
Vercel as its domain settings instruct. `vercel.json` also redirects `www` itself, as a
second line of defence.

## Enquiries: each building's form, the lead sheet and the inbox

Charlotte Square's intake, for a site with eleven buildings. **Every building's page has
its own enquiry form** (*Ask about Water Street.*, at `#enquire`), and the contact page
keeps the general one. Both post to `/api/inquiry/` (`api/inquiry.js`, a Vercel
function), which:

1. **saves the enquiry in the database** (`api/_lib/db.js`), the record the dashboard
   reads, when one is connected;
2. at the same time puts it on the **lead sheet** in the Evolution24 Google Workspace,
   on that building's tab (General when none was picked); sends the visitor a short
   **confirmation email** naming the building (`api/_lib/confirm.js`: no more than one
   per address in twelve hours, never to an address that unsubscribed, and never
   repeating what they typed); and, when switched on, adds them to that building in
   **Rent Manager** as a prospect (see *Rent Manager*);
3. then emails **the leasing team**, every address in `LEAD_TO`, with the building as
   the headline, every answer in words, and how steps 1 and 2 went. Reply-To is the
   prospect, so pressing reply answers them.

The visitor is told it worked if the database, the sheet or the email has it. Only when
all three fail are they asked to call, because only then is nothing written down.

**A building's form fits the building.** *Home you'd like to see* lists the homes it has
open, as the site lists them (*Unit 302RV · 1 bed · $1,590/mo*); the endpoint accepts
only those, so the lead sheet's *Home* column and the email always name a real unit.
*I'm interested in* starts at *Booking a tour*. A building with nothing open asks for
bedrooms instead and starts at *Joining the waitlist*. *Moving in* offers *As soon as
possible*, the next six months by name, or *Later*. Every *Contact*, *Send a message*
and *Join the waitlist* on a building's page goes to its form.

**Charlotte Square is left out** of the forms, the endpoint and the sheet: it has its
own site, form and lead sheet. The contact form's property menu skips it and points to
charlottesquareroc.com instead.

**The choices** are `LEAD_OPTIONS` in `scripts/build.py`. They feed the forms,
`api/leads-config.json` (what the endpoint accepts, with each building's open units)
and the generated block in the sheet script, so they cannot drift apart. The lead sheet
gained two columns at the end, *Home* and *Sent from* (the building's page or the
contact page); a tab made before them gets them on its next enquiry.

**Came via.** Once per visit the site notes the campaign tag (`utm_source`,
`utm_medium`, `utm_campaign`) or the outside site that brought the visitor, and the
first page they opened. It is kept in `sessionStorage`, not a cookie, and sent with the
form. When the page could not say (storage blocked, say), the endpoint looks up the
visitor's first pageview of the day in the statistics instead. It shows in the email,
the sheet's *Came via* column and the dashboard.

**Protection.** A honeypot field people never see; a same-origin check; five sends
per connection per ten minutes (in the database, or in memory without one); every
field capped and stripped of control characters; menus that accept only their own
choices; and the sheet script stores anything starting with `=`, `+`, `-` or `@`
as plain text, so a "name" can never run as a formula.

Without JavaScript the forms still post, and the endpoint sends the browser back to
the page they came from with `#sent` or `#not-sent`, where CSS `:target` shows the
notice.

### Setup, once

**1. The lead sheet.** Follow the steps at the top of `tools/lead-sheet/Code.gs`: a
new Google Sheet in the Workspace, paste the script, run `setup`, deploy it as a web
app (*Execute as: Me*, *Who has access: Anyone*). You get the tabs (Overview, General,
one per property, Lists), the dropdowns, the colours and the logo, plus a web-app
address and a token. Share it with the leasing team as Editors.

**2. Email.** The Resend account Charlotte Square already uses will do: make a key
there (API Keys → Create, sending access). Sending to anyone other than the account's
own address needs a domain verified in that account, with `LEAD_FROM` on it. If
`evolution24.net` is not verified there yet: Resend → Domains → Add, then add the
records it lists at the evolution24.net DNS host. They are separate from Google
Workspace's mail records (a DKIM key under `resend._domainkey`, and SPF and MX on a
`send` subdomain), so Workspace mail is untouched.

**3. Environment variables.** Vercel → the evolution24-net project → Settings →
Environment Variables, for Production (and Preview if you test there). Then
Deployments → ⋯ → **Redeploy**: a deployment never sees variables added after it was
built.

| Variable | Value |
| --- | --- |
| `LEAD_TO` | The leasing inboxes, separated by commas. Every address gets every enquiry |
| `LEAD_FROM` | `Evolution24 Properties <leasing@…>`, on a domain verified in Resend |
| `RESEND_API_KEY` | The key from step 2 |
| `LEADS_SHEET_URL` | The web-app address from step 1 (ends `/exec`) |
| `LEADS_SHEET_TOKEN` | The token from step 1 (Evolution24 menu → Show the connection token) |
| `LEADS_SHEET_LINK` | Optional: the sheet's own address, linked from every email |
| `REPLY_TO` | Optional: where replies to a visitor's confirmation go (the first `LEAD_TO` address if not set) |
| `DATABASE_URL` | The database (see *Statistics and the dashboard*); without it the form still works |

The inbox addresses live only in Vercel, never in this repository or the page source,
because a published address is the first thing a harvester finds.

**4. Test it.** Send the form on the live site. Both inboxes get the email, and the row
appears on the right tab with the Overview counting it.

Three local tests cover the same ground with no accounts or network:
`node scripts/test-inquiry.cjs` checks the endpoint (validation, email, failures);
`node scripts/test-lead-sheet.cjs` runs the sheet script itself behind the endpoint, in
an in-memory stand-in for Google Sheets, and checks that setup makes a tab for every
property and that each property's enquiry lands on its own tab and nowhere else; and
`node scripts/test-analytics.cjs` runs the whole chain with the database: a building's
form, the confirmation, Rent Manager, the dashboard's numbers, reports and unsubscribing.

### When it does not work

| What you see | What to change |
| --- | --- |
| The form says it is *not connected yet* | No variables set, or not redeployed since |
| Email arrives saying *Not added to the lead sheet: Wrong token* | Copy the token again into `LEADS_SHEET_TOKEN`, redeploy |
| Email says *Google asked for a sign-in* | Redeploy the script with *Who has access: Anyone*; or the Workspace admin blocks public web apps |
| Row in the sheet, no email | Vercel → Logs. `403 … your own email address`: no verified domain, or `LEAD_FROM` not on it. `401`: the key |
| A new property on the site has no tab | Nothing: the first enquiry for it makes its tab. Run `setup` after updating the script to tidy the order |

## Statistics and the dashboard

Charlotte Square's analytics, for eleven buildings. All first-party: nothing is sent to
Google Analytics or anyone else, and the Content Security Policy still allows only this
site.

**What is counted.** `assets/js/analytics.js` on every page sends a pageview, and these
named events, to `/api/collect/` (`api/collect.js`), which stores them in the database:

| Event | When |
| --- | --- |
| `phone_click`, `email_click` | a tap on the phone number or the email address |
| `apply_click` | an *Apply* link to Rent Manager's application, with its building and unit |
| `portal_click` | the residents' portal |
| `map_click` | *Show the map* or *Directions* |
| `gallery_open` | the photo gallery |
| `filter` | a unit-size filter (studio, 1, 2 or 3 bedrooms) |
| `form_start` | the first touch on an enquiry form |
| `outbound` | any other link to another site |

Every pageview and event on a building's page, and every *Apply* click, is filed under
that building. No cookie is set and no IP address kept: a visit is grouped by a code made
from the day, a secret salt, the connection and the browser, which changes at midnight.
Do Not Track and Global Privacy Control turn it off. Bots are not counted, and a page
the browser prerendered counts only once it is shown. The privacy page says all this.

**The dashboard** is at **`/admin/`**, behind one password (six wrong tries lock that
connection out for fifteen minutes; a sign-in lasts twelve hours). It shows the last 7,
30, 90 or 365 days:
- visitors, pageviews, enquiries, the enquiry rate, phone taps, Apply clicks and portal visits, day by day;
- **by building**: each one's visitors, Apply clicks, phone taps, enquiries and rate;
- the units people applied for, and size interest;
- where visitors and enquiries came from (search, social, listing sites, campaigns), and the
  steps from visit to form to enquiry;
- every enquiry, filtered by building, with buttons to mark it handled or send it again to the
  inbox, the sheet, the visitor or Rent Manager;
- what the emails did (sent, delivered, bounced, unsubscribed), once Resend's reports are connected;
- a link builder for tagged ads, posts and signs (`?utm_source=…`);
- **shared reports**: a day, week or month frozen into a page at `/r/<link>/` that anyone with
  the link can read and save as a PDF, holding totals only, never a person. Switching one off
  makes its link stop working at once.

### Setup, once

**1. The database: Postgres at Supabase.**

- **A project of its own.** In Supabase → *New project*, name it e.g. `evolution24-website`,
  pick the region nearest Vercel's (East US), and save the database password it makes in a
  password manager. Its own project keeps its tables and credentials apart from anything
  else in the account.
- **The address.** The project → *Connect* → **Transaction pooler** (port 6543; not *Direct
  connection*, which Vercel cannot reach). Copy the `postgres://…pooler.supabase.com:6543/postgres`
  address, put the password where it says `[YOUR-PASSWORD]`, and add it in Vercel as
  `DATABASE_URL`. A password with symbols in it must be URL-encoded there (`@` is `%40`).
  If you connect Supabase through Vercel's Marketplace instead, it sets `POSTGRES_URL`,
  which works the same.
- **Optional, stricter.** The connection is encrypted either way. To have the server's
  certificate checked too: Supabase → Database Settings → SSL Configuration → *Download
  certificate*, and paste the whole file into Vercel as `DB_CA_CERT`.

The tables are made on the first request; there is nothing to run. Each has row-level
security on with no policies, so Supabase's public Data API cannot read or write them;
the site connects as their owner, which row security does not apply to.

**2. The dashboard's secrets.** Open `scripts/hash-password.html` in a browser on your own
computer (no internet needed, and it can reach none), or run `node scripts/hash-password.mjs`.
It makes a password (save it in a password manager) and gives `ADMIN_PASSWORD_HASH`,
`SESSION_SECRET` and `VISITOR_SALT`. Add all three in Vercel, for Production.

**3. Email reports (optional).** Resend → Webhooks → Add endpoint
`https://evolution24.net/api/email-events/`, with every *email.* event. Put its signing
secret (`whsec_…`) in `RESEND_WEBHOOK_SECRET`. Until then the dashboard counts emails sent,
and says that delivery counts start once this is connected.

**4. Redeploy**, then open `/admin/` and sign in.

**Search Console.** Add evolution24.net as a property in Google Search Console; the
sitemap is `https://evolution24.net/sitemap.xml`. To verify with an HTML file, put the file
Google gives you in the repository root and push it.

`node scripts/test-analytics.cjs` runs every function in `api/` against a real Postgres
(PGlite, in the test's own process, reached over a socket the way Supabase's pooler is, so
the site's own driver is tested too), with stand-ins for Resend, the lead sheet and Rent
Manager. It needs `npm ci --prefix scripts` once, which installs PGlite into
`scripts/node_modules` and nothing into the site. `node scripts/test-admin-ui.cjs` drives the dashboard itself in Chromium

## Rent Manager

Three connections, all through Rent Manager's Web API (`evolution.api.rentmanager.com`):

### What is open, on the website

`scripts/availability.mjs` reads every building's units from Rent Manager (type, status,
occupancy and market rent) and rewrites each building's `units` and `units_as_of` in
`data/properties.json`; `.github/workflows/availability.yml` runs it at 7 and 10 am and
1, 4, 7 and 10 pm, rebuilds the pages, and pushes, so Vercel publishes the change. Each
building's page, the *Available now* list, the forms' *Home* menus, the dashboard and the
home page's counts all follow.

How it reads a unit is Charlotte Square's live-tested reader: vacant units are open now;
units being made ready, and units on notice with a move-out date to come, are open from
that date (*From Nov 15* in the tables); anything Rent Manager calls rented or leased, a
model or a down unit is never listed. A unit named with `-F` is furnished. A building's
`hide_units` in `data/properties.json` keeps a unit off by hand (spoken for, lease not in
Rent Manager yet). It writes nothing if the answer looks wrong: nothing open anywhere
while the site lists some, or more than a quarter of all units open at once.

**Setup:** GitHub → the repository → Settings → Secrets and variables → Actions → add
`RM_USERNAME` and `RM_PASSWORD` (a read-only Rent Manager user that can see every
building's units; Charlotte Square's website user will do if it can). Until they are
there, the job does nothing. To run it now: Actions → *Availability from Rent Manager* →
*Run workflow* (tick *Only report* for a dry run). A failed run emails the repository's
owner and the site keeps its last list. `node scripts/test-availability.cjs` tests it
against a fake Rent Manager.

### Leads, into Rent Manager

With `RM_PROSPECTS=on` in Vercel, every enquiry about a building is added to Rent Manager
as a prospect of that building (`api/_lib/rentmanager.js`): its name, email and phone, the
move-in month, the lead source, and a comment naming the home they asked about and the
enquiry number. The same person asking about the same building again within 90 days is
not added twice. Rent Manager files every prospect under a property, so the contact page's
enquiries with no building picked stay in the sheet only. The team email and the
dashboard say whether each one got there, and the dashboard can send one again.

| Vercel variable | Value |
| --- | --- |
| `RM_PROSPECTS` | `on` |
| `RM_USERNAME`, `RM_PASSWORD` | a Rent Manager user allowed to add prospects |
| `RM_LEAD_SOURCE_ID` | optional: the ID of Rent Manager's "Website" lead source |
| `RM_PHONE_TYPE_ID` | optional: the ID of the phone type to file numbers under |
| `RM_COMPANY`, `RM_LOCATION_ID` | only if not `evolution` and location 1 |

Try it on one test enquiry first and look at the prospect in Rent Manager: the API's field
reference is behind its login, so the request follows its published model (Prospects,
Contacts, PhoneNumbers) and has been tested against a stand-in, not the real thing.

### The Google sheets

`tools/rent-manager/` is the start of the sync that will fill the Google sheets from
Rent Manager's Web API, so nobody copies figures across by hand. It is one Apps Script
project, kept separate from every sheet and shared with no one:

- `RentManager.gs`: the only way in. It signs in, keeps the token between runs, reads
  long lists page by page, keeps within the company's hourly request limit and tries
  again when Rent Manager is briefly down. It only reads, it sends the token to
  `evolution.api.rentmanager.com` and nowhere else, and it never logs the password or
  token. Every later sync script goes through it.
- `Check.gs`: `checkRentManager`, the first thing to run. It asks Rent Manager
  read-only questions and writes the answers to a new sheet, *Rent Manager check*:
  - the hourly request limit;
  - every building in Rent Manager, matched to the website's IDs;
  - whether the website's units are found;
  - which parts of the API this user can read, with their record counts and field names;
  - the chart of accounts, charge types and reports;
  - how many bills were posted in the last 90 days, per building.

  It copies no names, contact details, balances or amounts, and masks long runs of
  digits, so the sheet can be shared to plan the next scripts. The website's list of
  buildings and units in it is generated by `scripts/build.py`.
- `appsscript.json`: the project's manifest. It asks Google for two permissions only
  (reaching outside services, and Google Sheets), and lets the project fetch from
  `https://evolution.api.rentmanager.com/` and nowhere else.

### Setup, once

1. **In Rent Manager,** make a user for these scripts with view rights only.
2. **In Google,** signed in as the Workspace account the sync will run as, open
   [script.google.com](https://script.google.com) → *New project*. Name it
   "Evolution24 Rent Manager" and share it with no one.
3. Project Settings (the gear) → tick *Show "appsscript.json" manifest file*. Paste
   `tools/rent-manager/appsscript.json` over it. If the company code is not `evolution`,
   change the address in `urlFetchWhitelist` to match.
4. Add two script files named `RentManager` and `Check`, paste the two `.gs` files in,
   and delete the sample `Code.gs`.
5. Project Settings → *Script properties* → add `RM_COMPANY` (`evolution`), `RM_USERNAME`
   and `RM_PASSWORD`, plus `RM_LOCATION` if the location is not 1. Type them in here and
   nowhere else: not in a sheet, an email or a chat.
6. Pick `checkRentManager` in the toolbar and press Run. Allow access when Google asks.
   The execution log prints the report's address.

`node scripts/test-rent-manager.cjs` runs both files against a fake Rent Manager built
from its API overview. It checks:
- sign-in, keeping the token, and signing in again when a token expires;
- reading long lists page by page;
- what "no access" and "nothing found" mean;
- retries when Rent Manager is briefly down, and the hourly limit;
- that only reads are sent, and the token goes nowhere else;
- that no personal details, amounts, password or token reach the report or the log.

| The log says | What to change |
| --- | --- |
| *Add RM_COMPANY, … in Project Settings → Script properties first* | Add the missing script properties |
| *Rent Manager refused the sign-in* | The user name, password or location, or the user lacks Web API access |
| *Could not reach Rent Manager* | `RM_COMPANY` and the manifest's `urlFetchWhitelist` must name the same company |
| *The hourly request limit is used up* | Run it again after the reset the message gives |

## Pay logs

`tools/pay-log/make.py` makes a pay log for each member of staff: an Excel file in the brand's colours
and logo, to upload to Google Drive and save as a Google Sheet. There are three tabs:

- **Pay log**: the person and their rate of pay (per hour or per week), then a block for each pay week
  (Saturday to Friday) with a row per day, already dated: six property and hours slots across it, the
  day's hours and pay worked out, and a note. Each week has a total line; the grand total sits at the top.
- **Weekly summary**: hours and pay for each property, week by week, with totals.
- **Monthly summary**: the same, month by month. New properties go in its empty rows and join the
  Pay log's list.

On a weekly rate, each week's pay is shared across its properties by hours.

```
python3 tools/pay-log/make.py                              # a blank template in tools/pay-log/out/
python3 tools/pay-log/make.py tools/pay-log/people.json    # one file per person, and the template
python3 tools/pay-log/test.py                              # fills two logs, checks every total (needs LibreOffice Calc)
```

`people.json` holds names and rates of pay, so it is kept out of git; `people.example.json` shows its shape.

Someone with two roles at two rates keeps two pay logs under the same name, each with its Role filled
in (people.json: `"role"`); the report adds them together.

**The labor report.** `tools/pay-log/Report.gs` is the master report: a separate Google Sheet that reads
every pay log in the shared drive it sits in (Google Sheets with "Pay Log" in the name, not the template,
in the folder above the report's and every folder under it, so each person's log can be in a private
folder) and breaks the labor cost down by property and by person, with charts. It only reads the pay logs.
Setup is at the top of the file: a new Google Sheet in a managers-only folder (Accounting), the script pasted into
Extensions > Apps Script, and `tools/pay-log/appsscript.json` as its manifest (read-only Drive). Then
Evolution24 > Refresh report, or Refresh every hour. Tabs: Report (labor cost and hours by property
and person, each person's total and pay log, a From/To period), By month, Properties (who shares office time), and Data (every line read).
Hours logged as "Office / all properties" (or "Office") are shared, with their pay, across the buildings
on the report's Properties tab by each one's share: equal to start with, unit counts to share by size,
0 to leave one out. The pay logs keep the line as logged; the report's Data tab says what each shared
line was logged as. Each person keeps one chart colour in every chart; scripts/build.py fills in the logo.

```
node scripts/test-pay-report.cjs                  # the report against real, filled pay logs (Python and LibreOffice)
PREVIEW=out node scripts/test-pay-report.cjs      # and a picture of each tab (Playwright)
```

## Instagram

`tools/instagram/make.py` draws the Instagram launch kit in the site's look. It makes the
profile picture and nine 3:4 posts that fill the profile grid as one picture: property
photos on ink, and a cream band that runs straight across the middle row, behind
Charlotte Square, the flagship, in the center.
It also makes a preview of the profile in light and dark mode, and a zip with
`captions.md`, which holds the bio, the captions, the alt text and how to post them.

```bash
python3 tools/instagram/make.py        # writes tools/instagram/out/ (needs Pillow and Playwright)
```

Names, photos, the logo and the phone number come from the site. Which photo goes in
which window, and the words on each post, are set at the top of `make.py`.

**Now renting.** `tools/instagram/leasing.py` draws a second set of nine for a leasing push,
each a whole post on its own. Five are listings, at the corners and in the center: a building's
photo with a tan "Now available" stamp carrying how many of its homes are free, and a card with the
city, the building, the kinds of home and the rent they start at. Between them a cross of
statements on ink and tan: *Now renting.* *Now available.* *Now touring.* *Apply online.* The
counts, kinds and rents come from `data/properties.json`, the site's "Available now" list, so run
it again after that list changes; a listing whose building has nothing free stops the run, as
does a photo that would have to be blown up past 1.3x. Which buildings and photos it shows are set
at the top of `leasing.py`. `captions-leasing.md` holds the captions, alt text and the order to
post them.

```bash
python3 tools/instagram/leasing.py     # writes tools/instagram/out/leasing/ (needs Pillow and Playwright)
```

**The video.** `tools/instagram/story/story.py` makes a 20-second video, cut to the beat,
in two shapes from the same timeline and soundtrack:

- `evolution24-story.mp4`, 1080 × 1920, for Instagram and Facebook Stories.
- `evolution24-landscape.mp4`, 1920 × 1080, for the Facebook feed.

It opens on "An evolution in *home*." and dives through the full stop into six properties,
each with its own transition. Then comes Charlotte Square, then "Let's find your place." The
music brakes to a stop, the page folds into a line, and the logo's bars slam down onto it
with a jingle. In the wide cut, tall photos sit beside their words and wide photos fill the
frame. Facebook has no "link in bio", so the wide cut gives the phone number instead.

```bash
python3 tools/instagram/story/story.py               # both, into tools/instagram/out/story/
python3 tools/instagram/story/story.py --format landscape
```

Needs Pillow, numpy, scipy, Playwright and ffmpeg.

- **Music:** "Day Trips" by HoliznaCC0, from the album *City Slacker*, dedicated to the
  public domain under [CC0 1.0](https://freemusicarchive.org/music/holiznacc0/city-slacker/day-trips/).
  The script downloads it once and checks its checksum. No credit is required.
- **Jingle:** the riser, the impact and the chime are made in `audio.py` from sine
  waves and noise, so they are ours.
- **Mastering:** the mix is set to −14 LUFS, with a limiter at −1.5 dBFS.
- **Timing:** `story.js` places every moment on the track's beat grid (90 BPM, G major)
  and can draw any frame on its own. Frames are drawn at 60 fps and blended in pairs to
  30 fps for motion blur.
- **Where things are set:** the layouts for each shape are the `FORMATS` table at the top
  of `story.py`.
- **Checking a moment:** `stills.cjs` draws single frames, which is quicker than a full
  render.

## Facebook ads

`tools/ads/ads.py` makes a *Now renting* ad for every building with homes open: a picture and a
15-second video, each in two shapes, `feed` (4:5, 1080 × 1350) for the Facebook and Instagram
feeds and `story` (9:16, 1080 × 1920) for Stories and Reels. Each names who to call, with their
phone and email: Charlotte Square's its leasing agent, the rest the Evolution24 agent. It also
writes `ads.md` and `ads.csv`, each ad's primary text, headline, description, button, link and
alt text, with how to set the campaign up in Ads Manager, and `overview.jpg`, every feed ad on
one sheet.

```bash
cp tools/ads/contacts.example.json tools/ads/contacts.json   # once: who to call (kept out of git)
python3 tools/ads/ads.py                                    # all, into tools/ads/out/
python3 tools/ads/ads.py --only water-street,biltmore --no-video   # redraw some; the words cover all
```

- **What is open** comes from `data/properties.json`, the site's "Available now" list: the kinds
  of home, how many, the lowest rent, and the date it was listed, which every ad shows. A
  building with nothing open is left out. Run it again after the list changes, and pause the ad
  of any building that fills up.
- **Housing.** Meta requires rental ads to run in the *Housing* special ad category: no
  targeting by age, gender or ZIP code, and a radius of at least 15 miles. The words say what
  the homes are, never who they are for, and every ad carries the Equal Housing Opportunity mark.
- **Links** carry `utm_campaign=now-renting-<slug>`, so the dashboard's Campaigns panel shows
  each building's ad on its own.
- **The video:** the building's three photos, graded like the Instagram kit, drift and dissolve
  in the picture, the line under the name changing with each, then an end card. Music: "Day
  Trips" by HoliznaCC0 (CC0 1.0), the story video's track. Needs Pillow, numpy, Playwright and
  ffmpeg.
- **Where things are set:** the photos, lines and pitch for each building are the `ADS` table at
  the top of `ads.py`; the two shapes are `FORMATS`.

**Specials.** `tools/ads/deals.py` makes the same kind of ads for a leasing special, from
`tools/ads/deals.json`: half off the first month on leases signed by a date, as an ad for each
building in one area (`AREA` in `deals.py`: Rochester) and one for all of them, and a special rent
on a home or two per building. The two are
never combined, and every ad says so in its small print. The ads name the deadline and the date
the special rents were set, and `ads.md` says to end the campaign on the deadline. For the next
special, edit `deals.json` and run it again.

```bash
python3 tools/ads/deals.py                  # all, into tools/ads/out/deals/
python3 tools/ads/deals.py --only special-biltmore,half-off-water-street --no-video
```
