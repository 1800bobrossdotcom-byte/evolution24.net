# Evolution24 Properties — evolution24.net

The redesign of evolution24.net, the family-owned property manager with apartments in
Rochester, Syracuse, Manlius and Geneva, New York. It replaces the Rent Manager
WordPress theme with a fast static site, built the same way as its sister site
[charlottesquareroc.com](https://github.com/1800bobrossdotcom-byte/50CharlotteSquare).

Nothing on the old site was kept except the photographs and the facts. Every photo
and every fact on the old site is here.

No framework and no runtime dependencies: plain HTML, one stylesheet and one script.
The HTML is generated by a Python script from two JSON files.

## Build

```bash
python3 scripts/photos.py        # when photos change (needs Pillow with AVIF support)
python3 scripts/build.py         # always — writes every page into the repo root
node scripts/render-og.cjs       # when a name, a cover photo or a unit count changes, then build again
node scripts/render-icons.cjs    # when the logo changes (needs Playwright)
python3 -m http.server 8000      # preview at http://localhost:8000
```

| Edit this | To change |
| --- | --- |
| `data/properties.json` | A building's name, address, map coordinates, description, amenities, **available units and rents**; each city's blurb and share-card photo |
| `source/photos/manifest.json` + `source/photos/<slug>/` | Photos and their alt text, then run `photos.py` |
| Constants at the top of `scripts/build.py` | Phone, email, office address, portal links, pet policy, FAQs |
| `assets/css/main.css` | The design. Everything below the `GENERATED` line is rewritten by the build |
| `assets/js/main.js` | Behaviour |

Never hand-edit the generated `*.html`, `sitemap.xml`, `llms.txt`, `speculation-rules.json`, `vercel.json`,
`_headers`, `_redirects`, `assets/img/og/` or `data/page-dates.json`. Do commit them all.

## Pages

| URL | What it is |
| --- | --- |
| `/` | Intro animation, hero slideshow, the three regions, photo band, every available unit, about, residents, contact |
| `/properties/` | All 11 buildings, filterable by region and by availability, plus the full unit list |
| `/properties/<slug>/` | One per building: photos with lightbox, description, amenities, available units with Apply links, map, nearby |
| `/apartments/rochester-ny/`, `/apartments/syracuse-ny/`, `/apartments/geneva-ny/` | One per city: its buildings, every unit open there, each address, and answers to the usual questions. These are the pages meant to rank for "apartments in Rochester, NY" |
| `/about-us/`, `/faqs/`, `/contact-us/` | Same URLs as the old site, so no rankings are lost |
| `/privacy/` | Fair housing, privacy and accessibility statement |
| `404.html` | Not found |

`/about-us/`, `/faqs/`, `/contact-us/` and `/properties/` keep their old addresses on purpose.
The old URLs that are going away are redirected:

| Old | New | How |
| --- | --- | --- |
| `/property-detail/?pid=8` | `/properties/water-street/` | 301 from `vercel.json`, matched on the query string; `assets/js/legacy.js` elsewhere |
| `/unit-detail/?uid=62` | `/properties/water-street/#units` | same, one per available unit |
| `/careers/` | `/about-us/` | 301 from `vercel.json` (or `_redirects`), plus a stub page |
| `www.evolution24.net/*` | `evolution24.net/*` | 301 from `vercel.json` (or `_redirects`) |

On Vercel the query-string redirects are real 301s, so the rankings of the old building
pages pass to the new ones. Other static hosts can't match a query string, so the stub
pages stay as a fallback: they are `noindex` and redirect in the browser. `robots.txt` no
longer blocks them, because a crawler that can't fetch an old URL never sees its redirect.

## Logo and animation

The logo is traced from the owner's PSD (`source/logo/Evolution24_Properties_logo.psd`,
four layers at 6000 × 2460). Each bar of the mark and each letter of the wordmark is its
own path. That is what makes it animate:

- **Intro.** Only when a visit starts on the home page, the bars rise one by one from the
  baseline, the letters settle in, and the curtain lifts. The whole thing takes 2.9 s, and
  1.75 s on a phone. A click or any key skips it. It is skipped entirely under
  `prefers-reduced-motion`, and a `sessionStorage` flag makes sure it never plays twice in a
  visit, or at all when the visit starts on another page (someone arriving from a search
  result for a building wants the building). The page underneath has already loaded, so the
  intro never delays content.
- **Header.** The bars rebuild on every page load and ripple on hover.
- **Everything else.** Masked headline rises, a Ken Burns hero slideshow, scroll reveals and
  image wipes, count-up stats, an index of every building under the hero (names rise in turn;
  hovering one inks it tan and shows its city and how many homes are open), photo rows that drift with the
  scroll (CSS scroll timelines, where supported), filter transitions and cross-page
  transitions (View Transitions API, where supported).

**Reduced motion is reduced, not removed.** When a visitor's device asks for less motion
(Windows "Animation effects" off, macOS/iOS "Reduce motion", Android "Remove animations"),
nothing slides, zooms, scrolls or auto-advances, but pages still fade in and hovers still
change colour. The intro is skipped and the slideshow waits for a click. Test both: Chrome
DevTools → Rendering → "Emulate CSS media feature prefers-reduced-motion".

Logo files: `assets/img/logo.svg` (for dark backgrounds, as supplied), `logo-on-light.svg`
(the cream swapped for ink, so it reads on white), `mark.svg`, `favicon.svg`,
`favicon.ico`, `apple-touch-icon.png`, `logo-192.png`, `logo-512.png` and `og.png`, the
social share card.

## Site load

| | Size (gzipped) |
| --- | --- |
| Home page HTML, with the whole stylesheet inlined | 26 KB (the CSS is 9 KB of it) |
| `main.js` (deferred) | 4 KB |
| Preloaded fonts | 44 KB, plus 21 KB for the italic on the home page |
| Hero photo (AVIF) | 32–66 KB on a phone (49 KB on an iPhone, down from 95 KB), 85–125 KB on a desktop |

The old site shipped jQuery, Slick, Font Awesome, Google Fonts and a full WordPress theme.
Here:

- **Photos** are AVIF, with WebP for older browsers, at 240, 480, 720, 960, 1200, 1400,
  1600 and 2000 px. Each `<picture>` has `sizes` worked out from the layout, so a phone
  never downloads a desktop image. 1200 and 1400 exist for phones: a full-width photo on a
  3× screen needs 1170–1320 pixels, and used to get the 1600. The home page's hero on an
  iPhone is 49 KB, down from 95 KB. AVIF is about a quarter smaller than WebP at the same
  look. Every `<img>` has `width` and `height`, so
  nothing jumps as it loads. Only the hero photo loads eagerly, with `fetchpriority="high"`
  and an AVIF preload. Everything else is lazy. EXIF data is stripped, which removes the
  GPS location phones embed.
- **Fonts** (Manrope, Instrument Serif) are self-hosted, subset and preloaded. Until they
  arrive, text is set in local fallback fonts resized to the same measurements
  (`size-adjust` and the ascent, descent and line-gap overrides). That matches their
  average width, not every line break, so Manrope is `font-display: optional`: being
  preloaded, it is almost always ready for the first paint, and when it isn't, that one
  page stays in the fallback instead of swapping. A swap once re-wrapped the home hero's
  paragraph and buttons and moved the whole hero (Lighthouse: layout shift 0.19); now it is
  0. The display serif keeps `swap`, because its headings are set line by line and can't
  re-wrap.
- **CSS is inlined** into every page, minified, so the first paint waits on no request.
  The CSP allows it by its hash. Painting that early means a slow connection can show half
  a hero, and the home and building heroes are bottom-aligned, so the rest arriving would
  push their words up the screen. Their words therefore stay invisible, though in place,
  until the section after the hero has started to arrive (`:has(+ *)` in `main.css`).
- **Next pages are ready before the tap.** Speculation Rules (`speculation-rules.json`,
  sent in a `Speculation-Rules` header) let Chrome and Edge prerender a page while a
  visitor hovers over its link or starts to press it, so most navigations are instant. `/api/`, the redirect
  stubs and files are excluded. Other browsers ignore it.
- **Phones.** Every link and button is at least 44 px tall on a touch screen (padding taken
  back with negative margin, so the design doesn't move). Long button labels wrap instead
  of pushing the page sideways, and nothing scrolls sideways at 360 px. On a building's
  page, a bar with **Call** and the building's next step (see what's available, join the
  waitlist, or visit Charlotte Square's site) slides up once the hero's buttons have
  scrolled away, and gets out of the way over the footer.
- **Maps** load nothing from Google until someone presses "Show the map".
- **Caching:** CSS and JS are requested as `?v=<content hash>` and cached for a year as
  immutable. Images are cached for 30 days.
- **No third-party requests at all.** No cookies, no analytics, no consent banner.

## SEO

- **One host.** `SITE = https://evolution24.net`, the apex that the old site already used
  as its canonical. `www` 301s to it.
- **Titles and descriptions** are written per page, include the city and the category
  ("apartments"), and stay under Google's truncation length. Descriptions are built from
  whole sentences (`fit()` in `build.py`), so none is ever cut mid-word, and lead with the
  facts people search for: bedrooms, address, how many are available, and the rent.
- **City pages** (`/apartments/<city>-ny/`) answer "apartments in Rochester, NY" and its
  like: every building and every open unit in that city, with `CollectionPage`, `ItemList`
  and `FAQPage` markup. Building pages link up to their city, in the breadcrumb and the
  text, and the footer links all three.
- **Structured data.** Every page carries one JSON-LD `@graph`: `WebSite`, a
  `RealEstateAgent` for Evolution24 (`#organization`, with address, phone, founding date,
  the four cities it serves, and `sameAs` pointing to Charlotte Square), `WebPage` and
  `BreadcrumbList`. The organization also has its logo, the office's coordinates and a
  leasing `ContactPoint`. Each building page adds an `ApartmentComplex` or `Residence` with
  its address, coordinates, photos, amenities, map link, price range, its city, and one
  `Apartment` for each available unit. `/faqs/` adds `FAQPage`, `/properties/` adds an
  `ItemList`. Every page names its share card as `primaryImageOfPage` and carries a
  `dateModified`. Validate at <https://validator.schema.org/>.
- **Coordinates** for each building were looked up from its street address in
  OpenStreetMap and are stored as `geo` in `data/properties.json`.
- **Sitemap** with Google image entries for 107 photographs. Each URL's `lastmod` is the
  day that page's content last changed, not the day of the last build:
  `data/page-dates.json` keeps a fingerprint of every page, and the date moves only when
  the fingerprint does. Search engines ignore a `lastmod` that changes on every build.
- **Share cards.** Every building and city, and the site itself, has its own 1200 × 630
  link preview (`assets/img/og/`, drawn by `scripts/render-og.cjs`): the photo, the logo,
  the name, and how many homes are open. So a link texted to a friend shows the building.
- **Alt text.** Every photo has a written description, in `source/photos/manifest.json`.
- **`robots.txt`** allows everything, including the AI crawlers. **`llms.txt`** is a
  plain-language fact sheet that lists every building and every available unit.
- **Charlotte Square.** Its page here points to charlottesquareroc.com. The Charlotte site's
  JSON-LD already names Evolution24 as its manager. Linking its `#management` node to
  `https://evolution24.net/#organization` would join the two sites into one entity.

After launch:

1. Verify `evolution24.net` in Google Search Console and Bing Webmaster Tools, then submit
   `sitemap.xml`.
2. Claim or update the **Google Business Profile** for the office at 176 N Water Street,
   with this URL. For "apartments in Rochester" it is worth more than anything on the page.
3. Check that `curl -sI https://www.evolution24.net/` returns a single 301 to the apex.

## Deploy

**Live on Vercel:** <https://evolution24-net.vercel.app/>. Vercel deploys every push, with no
build step: the generated site is committed, and Vercel publishes the repo root. Build logs
and the list of deployments are in the Vercel dashboard, under the **evolution24-net**
project. The branch Vercel treats as production is the repository's default branch.

Headers and redirects are generated in two dialects from the same lists in `build.py`:
`vercel.json` for Vercel, and `_headers` + `_redirects` for Cloudflare Pages or Netlify,
which Vercel ignores. `.vercelignore` keeps the sources out of the deployment: the logo
PSD, the original photos (13 of them carry GPS data), `scripts/` and `data/` are not
served.

The `vercel.app` address sends `X-Robots-Tag: noindex`, so search engines index only
`evolution24.net` and not a duplicate of it. `vercel.json` also sets `trailingSlash`, so
`/about-us` redirects to `/about-us/`, the canonical form.

| Header | Value |
| --- | --- |
| `Content-Security-Policy` | `default-src 'self'`, no `'unsafe-inline'` on scripts or styles. The one inline script, the intro flag in `<head>`, and the inlined stylesheet are allowed by their SHA-256 hashes, which the build computes from the same strings it emits. Frames are limited to Google Maps |
| `Speculation-Rules` | Points Chrome at `speculation-rules.json` (see *Site load*) |
| `Strict-Transport-Security`, `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Cross-Origin-Opener-Policy`, `Permissions-Policy` | Locked down |

Because the CSP forbids `style=""` attributes, animation stagger is done with generated
`.d0…d39` and `.i0…i11` classes rather than inline custom properties.

GitHub Pages can't set headers. There, only the `<meta>` CSP applies.

**DNS cutover.** The current site is WordPress. In Vercel, add `evolution24.net` as the
project's primary domain and `www.evolution24.net` as a redirect to it, then point DNS at
Vercel as its domain settings instruct. `vercel.json` also redirects `www` itself, as a
second line of defence.

## Enquiries: email and the lead sheet

Built on what Charlotte Square does, adapted for Vercel and for a site with no
database: **the lead sheet is the record, and the email is the alert.**

The contact form posts to `/api/inquiry/` (`api/inquiry.js`, a Vercel function).
In order:

1. The enquiry goes to the **lead sheet** in the Evolution24 Google Workspace, onto
   the tab for the property it is about, or **General** when none was picked.
2. The leasing team gets an **email**, to every address in `LEAD_TO`: which
   property, everything from the form, and whether step 1 worked. Reply-To is the
   prospect, so pressing reply answers them.

The visitor is told it worked if either one landed. Only when both fail are they
asked to call, because only then is nothing written down. When the sheet fails the
email says why; when both fail, Vercel's function logs do (Project → Logs).

**Charlotte Square is left out** of the form, the endpoint and the sheet: it has its
own site, form and lead sheet. The form's property menu skips it and points to
charlottesquareroc.com instead.

**What the form asks:** name, email, phone, property, what they are interested in,
bedrooms, when they are moving, how they heard about us, and a message. The choices
are `LEAD_OPTIONS` in `scripts/build.py`. They feed the form, `api/leads-config.json`
(what the endpoint accepts) and the generated block in the sheet script, so the three
cannot drift apart.

**Each building's enquiries land on its own tab.** Every way to write in from a
building's page (*Send a message*, the header's *Contact*, *Join the waitlist*) opens
the form with that building already picked, so its enquiries reach its tab rather than
General. On a fully leased building, *Join the waitlist* also picks *Joining the
waitlist*. General gets only what could be about anywhere: the home page, the city
pages, the contact page itself. Charlotte Square's page sends people to the form on
charlottesquareroc.com, so its enquiries reach its own lead sheet.

**Came via.** Once per visit the site notes the campaign tag (`utm_source`,
`utm_medium`, `utm_campaign`) or the outside site that brought the visitor, and the
first page they opened. It is kept in `sessionStorage`, not a cookie, sent only with
the form, and shows in the email and in the sheet's *Came via* column. The privacy
page says so.

**Protection.** A honeypot field people never see; a same-origin check; five sends
per connection per ten minutes (held in memory, so a speed bump rather than a wall);
every field capped and stripped of control characters; menus that accept only their
own choices; and the sheet script stores anything starting with `=`, `+`, `-` or `@`
as plain text, so a "name" can never run as a formula.

Without JavaScript the form still posts, and the endpoint sends the browser back to
`/contact-us/#sent` or `#not-sent`, where CSS `:target` shows the notice.

### Setup, once

**1. The lead sheet.** Follow the steps at the top of `tools/lead-sheet/Code.gs`: a
new Google Sheet in the Workspace, paste the script, run `setup`, deploy it as a web
app (*Execute as: Me*, *Who has access: Anyone*). You get the tabs (Overview, General,
one per property, Lists), the dropdowns, the colours and the logo, plus a web-app
address and a token. Share it with the leasing team as Editors.

**2. Email.** The Resend account Charlotte Square already uses will do: make a key
there (API Keys → Create, sending access). Sending to anyone other than the account's
own address needs a domain verified in that account, with `LEAD_FROM` on it. If
`evolution24.net` is not verified there yet: Resend → Domains → Add, then add the
records it lists at the evolution24.net DNS host. They are separate from Google
Workspace's mail records (a DKIM key under `resend._domainkey`, and SPF and MX on a
`send` subdomain), so Workspace mail is untouched.

**3. Environment variables.** Vercel → the evolution24-net project → Settings →
Environment Variables, for Production (and Preview if you test there). Then
Deployments → ⋯ → **Redeploy**: a deployment never sees variables added after it was
built.

| Variable | Value |
| --- | --- |
| `LEAD_TO` | The leasing inboxes, separated by commas. Every address gets every enquiry |
| `LEAD_FROM` | `Evolution24 Properties <leasing@…>`, on a domain verified in Resend |
| `RESEND_API_KEY` | The key from step 2 |
| `LEADS_SHEET_URL` | The web-app address from step 1 (ends `/exec`) |
| `LEADS_SHEET_TOKEN` | The token from step 1 (Evolution24 menu → Show the connection token) |
| `LEADS_SHEET_LINK` | Optional: the sheet's own address, linked from every email |

The inbox addresses live only in Vercel, never in this repository or the page source,
because a published address is the first thing a harvester finds.

**4. Test it.** Send the form on the live site. Both inboxes get the email, and the row
appears on the right tab with the Overview counting it.

Two local tests cover the same ground with no accounts or network:
`node scripts/test-inquiry.cjs` checks the endpoint (validation, email, failures), and
`node scripts/test-lead-sheet.cjs` runs the sheet script itself behind the endpoint, in
an in-memory stand-in for Google Sheets, and checks that setup makes a tab for every
property and that each property's enquiry lands on its own tab and nowhere else.

### When it does not work

| What you see | What to change |
| --- | --- |
| The form says it is *not connected yet* | No variables set, or not redeployed since |
| Email arrives saying *Not added to the lead sheet: Wrong token* | Copy the token again into `LEADS_SHEET_TOKEN`, redeploy |
| Email says *Google asked for a sign-in* | Redeploy the script with *Who has access: Anyone*; or the Workspace admin blocks public web apps |
| Row in the sheet, no email | Vercel → Logs. `403 … your own email address`: no verified domain, or `LEAD_FROM` not on it. `401`: the key |
| A new property on the site has no tab | Nothing: the first enquiry for it makes its tab. Run `setup` after updating the script to tidy the order |

**Not carried over from Charlotte Square (yet):** the `/admin/` dashboard, analytics,
the visitor's branded confirmation email and Claude's summaries, which all run on
Charlotte's Cloudflare database. Here the lead sheet is the dashboard.

## Instagram

`tools/instagram/make.py` draws the Instagram launch kit in the site's look. It makes the
profile picture and nine 3:4 posts that fill the profile grid as one picture: property
photos on ink, and a cream band that runs straight across the middle row, behind
Charlotte Square, the flagship, in the center.
It also makes a preview of the profile in light and dark mode, and a zip with
`captions.md`, which holds the bio, the captions, the alt text and how to post them.

```bash
python3 tools/instagram/make.py        # writes tools/instagram/out/ (needs Pillow and Playwright)
```

Names, photos, the logo and the phone number come from the site. Which photo goes in
which window, and the words on each post, are set at the top of `make.py`.

**The video.** `tools/instagram/story/story.py` makes a 20-second video, cut to the beat,
in two shapes from the same timeline and soundtrack:

- `evolution24-story.mp4`, 1080 × 1920, for Instagram and Facebook Stories.
- `evolution24-landscape.mp4`, 1920 × 1080, for the Facebook feed.

It opens on "An evolution in *home*." and dives through the full stop into six properties,
each with its own transition. Then comes Charlotte Square, then "Let's find your place." The
music brakes to a stop, the page folds into a line, and the logo's bars slam down onto it
with a jingle. In the wide cut, tall photos sit beside their words and wide photos fill the
frame. Facebook has no "link in bio", so the wide cut gives the phone number instead.

```bash
python3 tools/instagram/story/story.py               # both, into tools/instagram/out/story/
python3 tools/instagram/story/story.py --format landscape
```

Needs Pillow, numpy, scipy, Playwright and ffmpeg.

- **Music:** "Day Trips" by HoliznaCC0, from the album *City Slacker*, dedicated to the
  public domain under [CC0 1.0](https://freemusicarchive.org/music/holiznacc0/city-slacker/day-trips/).
  The script downloads it once and checks its checksum. No credit is required.
- **Jingle:** the riser, the impact and the chime are made in `audio.py` from sine
  waves and noise, so they are ours.
- **Mastering:** the mix is set to −14 LUFS, with a limiter at −1.5 dBFS.
- **Timing:** `story.js` places every moment on the track's beat grid (90 BPM, G major)
  and can draw any frame on its own. Frames are drawn at 60 fps and blended in pairs to
  30 fps for motion blur.
- **Where things are set:** the layouts for each shape are the `FORMATS` table at the top
  of `story.py`.
- **Checking a moment:** `stills.cjs` draws single frames, which is quicker than a full
  render.
